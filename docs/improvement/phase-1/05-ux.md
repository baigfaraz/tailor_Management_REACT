## Findings

### UX-001: Detail modal shows the wrong order/payment status after another customer was updated
- Severity: High
- Where: `ShowDetailModal.js:15-16, 200-217`
- Evidence: Harness marked Ayesha Malik's order complete, then opened Ali Raza. Database: `Pending`. Modal: "Order Status : Complete" while the "Order Complete" button is still shown (`raw/ui-audit.json` → `states.k005`, `screenshots/detail-modal-stale-status-1440.png`).
- Cause: `updatedOrderStatus` / `updatedPaymentStatus` are local state in a modal that stays mounted and is reused for every customer; they are never reset and take priority over `data`.
- Impact: Staff can believe an order is finished or paid when it is not.
- Suggested direction: Render status only from server data; refetch or update the list item after a mutation.
- Effort: S
- Related: K-005 (now confirmed), UX-002

### UX-002: Detail modal shows the previous customer while loading
- Severity: Medium
- Where: `AllCustomer.js:64-67`
- Evidence: With a 1.5 s API delay, opening row 2 showed "Ali Raza" (row 1) (`states.staleFlash`, `screenshots/detail-modal-stale-flash-1440.png`).
- Cause: `handleOpenModal()` runs before the fetch resolves; `customerData` still holds the last customer.
- Impact: Wrong measurements can be read on a slow Wi-Fi.
- Suggested direction: Clear data and show a loading state until the new customer arrives.
- Effort: S
- Related: UX-001

### UX-003: Loading and API errors look like an empty database
- Severity: High
- Where: `AllCustomer.js:72-170`, `SearchScreen.js:22-26`
- Evidence: `states.loadingShows` and `states.apiDownShows` both = "No data availaible to show!".
- Cause: One boolean (`someData.length > 0`) drives all states; catch blocks only log.
- Impact: On the LAN setup, a tablet that cannot reach the PC tells staff the shop has no customers.
- Suggested direction: Explicit `loading / error / empty / ready` states with retry.
- Effort: S
- Related: ARCH-008, ARCH-001

### UX-004: Add-customer form gives no validation or feedback
- Severity: High
- Where: `DetailModal.js`
- Evidence: Empty submit → `POST 400`, the confirm dialog stays open with "Click on confirm if you want to add!" and no message (`states.emptySubmit`). Success → fields clear, large modal stays open, no confirmation (`states.doubleSubmit.addModalStillOpen = true`). Measurements and price are `type="text"`. "Close" discards all typed data without warning. Required fields are not marked. Placeholder "Enter First Name" but the field is the full name.
- Cause: No validation layer; errors only `console.error`; flow designed around a second confirm dialog.
- Impact: The only way to create data fails silently; staff retype or lose entries.
- Suggested direction: Inline validation with required markers, numeric inputs with unit suffix, one Save button with saving state, success toast, warn before discarding.
- Effort: M
- Related: ARCH-002, UX-010, RESP-004, SEC-003

### UX-005: Delete is one click with no confirmation or undo
- Severity: High
- Where: `AllCustomer.js:154-160`
- Evidence: Trash icon `onClick` calls `DELETE` at once; status changes (less harmful) do have a confirm dialog.
- Cause: Confirmation added to some actions only.
- Impact: Permanent data loss from a stray tap on a tablet; the icon sits next to clickable cells.
- Suggested direction: Confirm dialog naming the customer, or soft delete with undo toast.
- Effort: S
- Related: K-003, A11Y-001

### UX-006: Status changes are one-way and the confirm text is vague
- Severity: Medium
- Where: `ShowDetailModal.js:240-261, 270-272`
- Evidence: Buttons appear only when status is `Pending`; once `Complete` there is no way back in the UI. Confirm text: "Are you sure you want to proceed?"
- Cause: Toggle logic exists in code (`Pending ? Complete : Pending`) but the button is hidden.
- Impact: A mis-tap cannot be corrected.
- Suggested direction: Status control that can switch both ways; confirm text names the action and customer.
- Effort: S
- Related: FEAT-008, FEAT-009

### UX-007: Search promises name search but only accepts an ID
- Severity: Medium
- Where: `SearchScreen.js:47`, `Searchbar.js:16`
- Evidence: Description "Search customer by Name or Customer-ID", placeholder "Enter Customer-ID"; name input → `GET /:name` → 500 → "Customer Not Found.".
- Cause: Backend only supports lookup by numeric ID.
- Impact: Staff must remember numbers.
- Suggested direction: Search by name/phone inside the customer list (NEW-002).
- Effort: M
- Related: K-007, NEW-002

### UX-008: Navigation misleads and has dead ends
- Severity: Medium
- Where: `Header.js`, `App.js`, `WelcomePage.js`
- Evidence: "Logout" links to `/` (no session exists). No active state. `/does-not-exist` renders a blank page (`states.unknownRouteText = "(blank)"`). Welcome page adds a click before any work.
- Cause: Placeholder navigation never finished.
- Impact: Confusing; blank pages look like crashes.
- Suggested direction: AppShell with Customers / New customer nav, active state, 404 page; start on the dashboard or list.
- Effort: S
- Related: FEAT-001, FEAT-002, K-018

### UX-009: Copy, terminology and spelling
- Severity: Low
- Where: various
- Evidence: "availaible", "Our Platform give ease for tailors", "every details", "such like"; "Customer No" / "Customer-ID" / "Customer Details" used for the same thing; "Thankyou!" in API error; neck options "Color"/"Ban" (likely "Collar"/"Band"; confirm with owner).
- Cause: No copy review.
- Impact: Looks unfinished.
- Suggested direction: Glossary (Customer #, Order, Measurements) and copy pass.
- Effort: S
- Related: K-017

### UX-010: Confirm button can send a second request
- Severity: Low
- Where: `DetailModal.js:408`
- Evidence: Double click on "Confirm" sent 2 POSTs: `201` then `400` (`states.doubleSubmit.posts`). Only 1 customer was created because the first success had already cleared the form.
- Cause: No disabled/saving state.
- Impact: Today harmless by accident; becomes a duplicate once the form keeps values (e.g. edit).
- Suggested direction: Disable Save while a request is in flight.
- Effort: S
- Related: UX-004
